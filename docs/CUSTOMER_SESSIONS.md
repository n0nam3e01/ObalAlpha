# Сессии покупателей: размещение и проверка

## Что изменилось

Покупательский access JWT действует 15 минут и хранится только в памяти вкладки. Сервер дополнительно проверяет активную запись CustomerSession. Refresh — случайный 256-битный секрет в HttpOnly-cookie, абсолютный срок 7 суток; в PostgreSQL хранится SHA-256. Планировщик удаляет истёкшие записи. Выход отзывает одну сессию, «Выйти на всех устройствах» — все текущие сессии покупателя. Старые JWT без sid отклоняются, старое значение obal_token удаляется из localStorage.

Cookie не ротируется при каждом продлении: это исключает взаимное отключение параллельных вкладок. Отзыв в БД немедленно запрещает как refresh, так и все access JWT этой сессии. Отказы refresh и logout не посылают удаление cookie, чтобы запоздавший ответ не удалил cookie более нового входа. После выхода оставшийся секрет непригоден на сервере. Новый вход перезаписывает его.

Если другая вкладка вошла под другим покупателем, автоматический refresh не повторяет прежний POST от его имени: приложение сбрасывает локальную личность и предлагает войти снова. Перезагрузка страницы может явно восстановить новый аккаунт из общей browser cookie.

## Перед публикацией

Таблица CustomerSession создаётся с RLS без публичных политик в той же транзакции, что таблица и индексы. Prisma работает через владельца БД; публичные Supabase REST роли не получают доступ к реестру сессий.

1. Применить миграцию `20261022120000_customer_sessions` (и предыдущую order_lifecycle, если она ещё не применена). Оба файла аддитивные. При откате API нельзя возвращать принятие старых JWT без согласованного решения о безопасности.
2. Обновить backend и frontend вместе. После обновления старым входам потребуется повторная авторизация.
3. Предпочтительно разместить `/api` под тем же origin/site, что frontend, через рабочий reverse proxy, и оставить `SESSION_SAME_SITE=lax`, `VITE_API_URL` пустым. Сам по себе пустой VITE_API_URL не создаёт proxy: существующий production `vercel.json` пока содержит только SPA fallback.
4. Для текущей прямой связи Vercel frontend → Render API в `render.yaml` явно задано `SESSION_SAME_SITE=none`. Cookie всегда Secure в production. Задать точные frontend origins в `CORS_ORIGIN`; CORS включает credentials. Не использовать wildcard. Публичный VITE_API_URL должен указывать HTTPS API без `/api`.
5. Браузеры, блокирующие third-party cookies, могут не сохранять вход при разнесённых сайтах даже с SameSite=None. Для них необходим общий site/proxy. Проверка этого размещения на production остаётся открытой; локальный loopback-тест её не заменяет.

`POST /auth/refresh` использует только HttpOnly-cookie. `POST /auth/logout` и `/auth/logout-all` требуют access Bearer. Для auth маршрутов проверяется Origin по точному allowlist; cookie-запрос без Origin с Sec-Fetch-Site=cross-site отклоняется. Доступ к администраторскому кабинету и заведению этим изменением не мигрирован.

## Проверки

- Backend: хэш секрета, HttpOnly/Secure/Path/SameSite, чужой Origin, срок жизни access, отклонение старого JWT, refresh, немедленный отзыв, изоляция двух сессий, logout-all, истёкшая сессия и отсутствие опасного удаления cookie в ответе на старый refresh.
- Frontend: память вместо localStorage, один refresh при параллельных 401, не больше одного повтора, защита нового входа от старого ответа и запрет повторения мутации под другим аккаунтом.
- Playwright: вход, HttpOnly-cookie, перезагрузка без потерянной авторизации, существующий цикл заказа/отмены/оценки, смена аккаунта в общей cookie-сессии без лишнего заказа, выход и повторная перезагрузка.

Итог 22 октября: backend 31/31 на чистой PostgreSQL 16.14, frontend 10/10, browser 1/1 (45,9 с), сборка успешна. Production-часть размещения ещё не проверена.
