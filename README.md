# Öbal Alpha

Еда из заведений рядом со скидкой. Заберите сегодня в указанное время.

React/Vite → Express/Prisma → PostgreSQL. Только самовывоз, оплата в заведении по цене на экране, без дополнительного сбора покупателю. Telegram не подключён. Supabase используется как PostgreSQL; авторизация покупателей пока через пароль и JWT в Express.

## Запуск

Нужна PostgreSQL. Заполните `backend/.env` по `.env.example`: DATABASE_URL, DIRECT_URL и случайный JWT_SECRET.

```powershell
cd backend
npm ci
npm run build
npm run db:migrate
npm start
```

В другом терминале:

```powershell
cd frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Интерфейс: http://127.0.0.1:5173. API: http://127.0.0.1:3000/api/health. Vite проксирует `/api`, frontend `.env` локально не обязателен. При сбое API показывается ошибка, а не подставной каталог.

`npm run seed` с ALLOW_DEMO_SEED=true **удаляет заказы и наборы** и создаёт примеры. Только для одноразовой локальной базы. В production заблокирован. Коды заведений печатаются в терминале. Окна выдачи вечерние, автоматически не переносятся на следующий день.

## Проверки

В backend: `npm test`. Интеграционный тест требует TEST_DATABASE_URL отдельной базы с именем `obal_test` или `obal_test_*` с применёнными миграциями. Создаёт и удаляет только свои записи. Без переменной явно пропускается.

Проверено на настоящей PostgreSQL: регистрация/вход, доступ только к своим заказам, конкурирующие брони последней порции, повторная отмена и выдача, цены без сборов, закрытые окна, отсутствие секретов в публичных ответах. Сборка frontend проходит. Это не проверка production-инфраструктуры.

## Правила MVP

- Бронирование блокирует строку набора до проверки остатков и создания заказа. Цену и комиссию считает сервер.
- Клиент отправляет ключ повтора при бронировании: повтор после сетевого сбоя возвращает тот же заказ без второго списания остатка.
- Отмена/выдача — условные переходы статуса: повтор не меняет остатки или экономию второй раз.
- Окна — время Астаны UTC+5, reserved_until хранится как UTC timestamp. Просроченная бронь становится NO_SHOW и не возвращает еду в каталог.
- Набор с действующими/выданными заказами нельзя переоценить или изменить: создайте новый.
- Заведение может снять любой набор с продажи, сохранив уже оформленные заказы. Цену и остаток можно менять только до первой брони.
- Отчёт считает выданные заказы и сохранённую комиссию, не фактическое поступление денег.
- Старые поля доставки оставлены ради истории. Новые заказы только PICKUP, service_fee=delivery_fee=0.

## Хостинг

| Часть | Сервис | Настройки |
| --- | --- | --- |
| Frontend | Vercel | Корневой `vercel.json` собирает `frontend` и публикует `frontend/dist`; в настройках проекта Root Directory должен быть корень репозитория. Если уже выбран `frontend`, его `frontend/vercel.json` и обычный Vite build тоже работают. |
| Backend | Render Web Service | Корневой `render.yaml`: папка `backend`, build `npm ci --include=dev && npm run build`, start `npm run db:migrate && npm start`, health `/api/health` |
| База | Supabase PostgreSQL | Session pooler 5432 для DATABASE_URL и DIRECT_URL; direct при доступном IPv6 |

Backend: NODE_ENV=production, HOST=0.0.0.0, TRUST_PROXY_HOPS=1 (только за одним доверенным прокси), CORS_ORIGIN=https://obal-alpha.vercel.app, DEMO_MODE=false. Render Blueprint генерирует JWT_SECRET, а DATABASE_URL и DIRECT_URL запрашивает при первом развёртывании. Для Supabase PostgreSQL используйте Session pooler на порту 5432; пароль вводится только в Render. Для нескольких реплик миграции переносим из start в один pre-deploy job.

Frontend: VITE_API_URL=https://адрес-api без `/api`, затем новая сборка. Переменная встраивается при сборке. Секреты в VITE_* запрещены.

Для пилота с реальными заказами нужен постоянно работающий API: бесплатный Render засыпает, процессный cron во сне не работает. Проверки срока в запросах бронирования/выдачи действуют независимо. Пока одна реплика: rate limit хранится в памяти. При росте нужны общие лимиты и отдельный планировщик.

Миграция `20260927150000_supabase_rls` включает RLS на таблицах приложения без публичных политик: клиентский Supabase Data API не получает доступ к данным. Backend подключается как владелец таблиц. При работе только через Prisma также можно отключить Data API в настройках Supabase. Демотокены seed в production не использовать. Токены заведений, ранее попавшие в публичные ответы старого API, нужно перевыпустить перед запуском.

Реальное заведение подключается вручную, без демо seed:

```powershell
cd backend
npm run venue:add -- --name "Пекарня" --category BAKERY --address "Адрес, Астана" --district "Есиль" --lat 51.1 --lng 71.4 --phone "+77000000000" --commission 20
```

Команда создаёт случайный код доступа. Передайте его менеджеру отдельно; он входит через `/partner`, публикует наборы, меняет цену и остаток до первой брони, снимает набор с продажи и подтверждает выдачу по коду покупателя.

## Администрирование

Админ-кабинет: `/admin`, отдельно от входа покупателей и заведений. Первый логин — `adminsuperapp1`. После применения миграций создайте аккаунт из доверенного терминала в `backend`:

```powershell
npm run admin:create
```

Команда попросит пароль (12–128 символов) без отображения ввода. Пароль не хранится в репозитории и не передаётся через чат. Команду запускают там, где `backend/.env` указывает на нужную PostgreSQL; повторный запуск не перезаписывает существующий аккаунт. Если база production, используйте только доверенный компьютер и проверьте `DATABASE_URL` до запуска, не выводя сам адрес с паролем в логи.

Админ может создать заведение в Астане, одобрить/скрыть его, добавить набор, одобрить/отклонить набор заведения, увидеть пользователей и их публичные ID. При создании заведения выдаётся одноразово показанный код входа. Кнопка «Новый код входа» перевыпускает код и токен заведения — старый код и активные сессии владельца перестают работать. Храните код как пароль и передавайте владельцу по защищённому каналу. Новые наборы владельца скрыты от покупателей до одобрения; уже оформленные заказы при скрытии сохраняются. Вход администратора ограничен по попыткам, JWT живёт 12 часов.

## До публичного пилота

Для открытого публичного запуска ещё нужны подтверждение контакта и восстановление пароля, текст политики обработки данных с реквизитами оператора, реальное подключение заведений, резервные копии и проверка восстановления. Карта позволяет выбрать любое заведение из списка и открыть маршрут в Google Maps; одновременные маркеры потребуют Google Maps API key. Курьеры, онлайн-оплата и Telegram отсутствуют.
